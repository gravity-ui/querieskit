# Правила работы с i18n

Подробные правила именования кейсетов и ключей для агентов, работающих с локализацией в `@gravity-ui/querieskit`. Краткая выжимка — в разделе [`## i18n`](../AGENTS.md) файла `AGENTS.md`, здесь — полный справочник с примерами.

## Техническая структура

Каждый виджет хранит свою локализацию в подпапке `i18n/`:

```text
widgets/
  WidgetName/
    i18n/
      en.json
      ru.json
      dicts.ts
      index.ts
```

- [`dicts.ts`](../src/widgets/QueriesHistory/i18n/dicts.ts:1) — собирает словари по языкам: `export default {en, ru}`.
- [`index.ts`](../src/widgets/QueriesHistory/i18n/index.ts:1) — регистрирует кейсет через [`addI18Keysets`](../src/i18n/index.ts:11) и экспортирует типизированную функцию `t`:

  ```ts
  import {addI18Keysets} from '../../../i18n';

  import dicts from './dicts';

  export default addI18Keysets('qp:widget-name', dicts);
  ```

- Имя кейсета всегда начинается с префикса `qp:` (namespace библиотеки) — тип `addI18Keysets` требует `` `qp:${string}` ``.
- В компоненте используется как `i18n('key_name')`, см. [`QueriesHistory.tsx`](../src/widgets/QueriesHistory/QueriesHistory.tsx:41).
- `modules` и `components`, у которых есть собственный переиспользуемый сценарий, также могут заводить свою папку `i18n/` по этой же схеме — правило применяется на всех трёх уровнях (`components` / `modules` / `widgets`).

## Кейсеты

Кейсеты делятся на 4 типа:

1. **Общие для всей системы** — используются во многих разделах, часто повторяются. Например: `common`, `common.units`, `common.actions`.
2. **Общие для раздела** — часто повторяются на страницах одного раздела. Например: `queries.common`.
3. **Специфичные для страниц раздела**. Например: `queries.editor`.
4. **Для переиспользуемых компонентов**. Например: `queries.status-icon`.

В контексте `qp:` namespace эквивалент раздела — виджет/модуль/компонент, например `qp:queries-history`, `qp:queries-history.history-list`.

### Рекомендации по кейсетам

- Для каждого кейсета обязательно указывать его контекст (для чего он и где используется — в комментарии рядом с регистрацией или в PR/документации).
- Не злоупотреблять гранулярностью: не создавать кейсет на несколько ключей без необходимости — объединять с существующим кейсетом раздела/виджета.
- Для секций или попапов одного раздела не заводить несколько кейсетов — использовать общий кейсет раздела.
- Называть кейсеты как можно короче: не `queries.history.filters`, а `queries.filters`.
- Для переиспользуемых компонентов не начинать нейминг со слова `component.` — начинать с раздела/сущности, к которой относится компонент: не `component.queries.status-icon`, а `queries.status-icon`.

## Ключи

Формат: `<контекст-элемента>_<содержание-текста>`.

- Контекст стараться брать из готового списка ниже; если не подходит — придумать свой короткий и понятный; если контекст определить не получается — не писать его вовсе.
- Не использовать контекст `label_`.
- Содержание текста в имени должно однозначно и лаконично отражать смысл (для длинных фраз — краткое описание сути, а не дословный текст).

### Примеры

| Текст | Ключ |
|---|---|
| Нотификация, заголовок: «Не удалось выполнить запрос» | `alert_query-execution-error` |
| Нотификация, сообщение: «Запрос выполняется дольше обычного, результат появится позже» | `alert_query-long-running` |
| «История запросов будет очищена через 30 дней после создания» | `alert_history-retention-notice` |
| Описание секции про сохранение и повторный запуск сценариев запросов | `context_reuse-saved-queries` |
| Активное действие «Повторить запрос» | `action_query-rerun` |

### Рекомендуемые контексты

- `context` — контекстная информация: подсказки, абзацы с пояснением назначения раздела/элемента.
- `alert` — обратная связь системы: нотификации по завершению запроса к серверу, предупреждения в обзоре ресурса (например, скорая блокировка аккаунта).
- `action` — действия пользователя: кнопки, ссылки, пункты действий в таблице, действия в правом верхнем углу обзора ресурсов.
- `field` — названия полей ресурса: колонки таблиц, формы редактирования, обзор.
- `title` — заголовок секции, страницы, попапа, компонента подтверждения (confirm), пункт меню.
- `confirm` — призыв к действию, например описание подтверждения операции.
- `value` — значения radio/switch, статус или другое переводимое значение поля.

## Технические префиксы

- **`raw_`** — если нужно избежать прогона текста через типограф.
- **`md_`** — если нужно выделить текст жирным/курсивом или добавить ссылку. Текст прогоняется через YFM и превращается в HTML-теги; на стороне компонента нужно подключать через `Yfm`-компонент. Атрибуты ссылки задаются так:

  ```json
  {
      "md_query-syntax-help": "Подробнее о синтаксисе смотрите в [документации](https://example.com/docs/query-syntax){target=_blank rel=\"noreferrer noopener\"}"
  }
  ```

- **Не использовать HTML-разметку в тексте напрямую** — для форматирования есть только `md_` + YFM.

## Допустимые символы

Каждый текст проверяется на отсутствие неразрешённых символов:

```ts
/**
 * [\u0400-\u04ff] – Кириллица
 * \u00a0 – Неразрывный пробел
 */
export const SAFE_SYMBOLS_REGEX = /^[a-z0-9\u0400-\u04ff[\](){}<>!@#$%^&*~_\-−–—+='"`«»„”‘’“?.,:;|\\/ ₽™®©№\u00a0]*$/i;
```

Перед добавлением новых строк в `en.json`/`ru.json` проверять их на соответствие этому регулярному выражению.

## Чек-лист при добавлении новых текстов

1. Определить, в какой кейсет должен попасть ключ (существующий кейсет виджета/модуля/компонента или общий — не плодить новые без необходимости).
2. Подобрать короткий контекст ключа из списка (`context`, `alert`, `action`, `field`, `title`, `confirm`, `value`) либо не указывать его, если не подходит.
3. Сформулировать лаконичное однозначное содержание в имени ключа (kebab-case после `_`).
4. Добавить перевод в `en.json` и `ru.json` одновременно.
5. Проверить текст на допустимые символы (`SAFE_SYMBOLS_REGEX`).
6. Если нужна разметка (ссылка/жирный/курсив) — использовать `md_`-префикс и YFM, не HTML.
7. Если нужно отключить типограф — использовать `raw_`-префикс.
